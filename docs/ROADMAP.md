# Roadmap

This page lists only what is missing. For what PA Webinar already does, see the [README](../README.md) and the [feature tour](FEATURES.md). For what was released and when, see the [changelog](../CHANGELOG.md) or the public `/changelog` page of any installation.

## How this roadmap works

- Items carry no version numbers. A version number promises an implied date, and when the date slips the page is no longer true. Planned items, those under [Installation and operations](#installation-and-operations), [Next](#next) and [Later](#later), carry the month they were opened, as *open since \<Month YYYY\>*, so a delay stays visible. Items under [Further out](#further-out) and [Conditional](#conditional) are not planned and carry no date.
- Shipped items leave at release time. The change that writes the release notes also removes the items it ships. From then on, the changelog records that they shipped, and the README and the feature tour describe what they do.
- An item that is not done when planned changes position, and leaves this page only when it ships.
- Each owner page lists its own known limitations. The [table below](#known-limitations-of-shipped-features) collects those worth knowing before you rely on a feature, and links the page that owns each one.

How roadmap decisions are made is described in [Governance](../GOVERNANCE.md). The documentation rules are part of the method in [How we develop PA Webinar](development/methodology.md).

## Installation and operations

This is the work in progress, and the area furthest behind what the project claims. One server is an installation path that another administration can follow on its own: `infra/onprem/k3s/pa-webinar-up.sh` installs k3s and the chart with one command, with object storage and TURN as options, and `scripts/verify-install.sh`, `scripts/backup.sh` and `scripts/restore.sh` check, back up and restore it. That path has been tested in lab, and not yet at a real event. No path yet takes another administration on its own from an empty managed cluster to a working event. Until one does, "reusable software" remains a statement of intent for larger installations. [Reusing PA Webinar](REUSE.md) shows what is proven today. [Installing PA Webinar](install/README.md) and [Deploying with Helm](DEPLOYMENT.md) cover what can be installed.

All items in this section are *open since July 2026*.

| Item | Where things stand |
|---|---|
| **An installation exercised from scratch** | The chart renders on every profile and the manifests it produces are valid. The simple profile has been installed from scratch in lab, on minikube and on k3s with one and with three VMs, through to a working event ([What has been exercised](install/README.md#what-has-been-exercised-and-what-is-only-validated)); on one server the one-command installer repeats that install, with locally built images, and checks it with a call between two browsers. What is missing is a from-scratch walk of the standard and full profiles on a managed cluster, a first real event on one server, and a recurring test that keeps every path working. A one-off install does not stay valid: certificate issuance, reachability of the bridge, email delivery and everything else that depends on the environment need to be checked again as the chart changes. |
| **Chart defects found by the lab installs** | The chart fixes or guards against most of the defects that the lab installs found, and [Chart issues found by the lab installs](INFRASTRUCTURE.md#chart-issues-found-by-the-lab-installs) lists them with their workarounds. One still has the widest effect:<br/>- **Conference credentials are not stable by default.** On every render, the Jitsi subchart regenerates any internal conference credential that is not pinned (XMPP passwords, the TURN secret), so an upgrade restarts Prosody, Jicofo and the bridge and drops live conferences. The post-install notes list the unpinned ones, and `jitsi.requirePinnedCredentials` makes the chart refuse to render until they are pinned. `infra/helm/pa-webinar/values-production.yaml` and the minikube, k3s, GKE and EKS overlays turn that guard on; the chart defaults and the simple, standard, full and AKS profiles list the keys to pin but leave it off. |
| **Images that can be pulled, verified and pinned to a version** | None of the published images accepts an anonymous pull, so someone who clones the repository cannot download any of them. The published images are neither scanned nor signed: the security scan in CI runs on a local, unpublished build of the app image. They are built for a single architecture (`linux/amd64`). The in-cluster PostgreSQL and Redis images are pinned by digest, because their public catalog keeps only a `latest` tag, and no procedure yet says how to move those pins forward. |
| **Portability across providers** | The object-storage layer is written for several providers ([Object storage](configuration/storage.md)), and video uploads from the administration area choose their protocol per provider: Azure block upload, or a signed S3 upload in one request or in parts. The S3 path has been exercised by hand against S3-compatible servers, but no automated test runs against a real storage service: the unit tests replace the provider SDKs with mocks, so the compatibility matrix is stated, not verified. Storage access also needs static keys: workload identities and managed identities are not used. Below the application, `infra/tofu` has reference modules for AKS, GKE and EKS, but only the AKS topology has run events: the GKE and EKS modules, their GPU pools included, have been validated only without a cloud account. The project needs to state what is actually portable and fix the places where it is not. |
| **Ingress beyond ingress-nginx** | The chart expresses several settings only as ingress-nginx annotations. For the portal it drops them when the Ingress class is listed in `ingress.nonNginxClassNames` and renders them for any other class, and the redirect of the conference domain's root is an ingress-nginx annotation in any case. On any other controller, these are lost:<br/>- the header buffers sized for Next.js, without which administration pages answer 502;<br/>- HSTS;<br/>- the maximum upload size;<br/>- the redirect of the conference domain's root.<br/>The timeout for long-lived connections, which the room's live channels depend on, and the rate limit are not in the chart defaults at all. They appear only in example profiles: the rate limit in `infra/helm/pa-webinar/values-production.yaml` and `infra/helm/pa-webinar/examples/values-full.yaml`, the timeout in `infra/helm/pa-webinar/values-production.yaml` alone. Whoever copies them loses them on another controller in the same way, and whoever does not copy them goes without. Inherited annotations are also hard to remove: Helm merges maps, so an empty `annotations: {}` in an override clears nothing, and each key has to be set to `null`. With a controller that speaks only Gateway API, the chart produces nothing usable, because it has no routing resources. Two changes would fix this: settings of their own for what is now written as annotations, and Gateway API routes alongside the `Ingress` resources. |
| **Backup and restore of the object store** | The database, the installation's keys and an object store on a volume of the cluster are covered: `scripts/backup.sh --include-storage` copies the Garage add-on of one server together with a database dump (encrypted when a key is given) and the state folder, and `scripts/restore.sh --include-storage` puts both back with the writers stopped ([Backup and restore](install/k3s.md#backup-and-restore)). What is missing is the rest. A provider's bucket (Azure Blob, S3, Google Cloud Storage) is backed up with that provider's tools, with no procedure here that takes it at the same moment as the database. The Garage copy stops the store for its whole duration, uploads and playback included, and it was measured only on a small store, so how long a real one stays down is unknown. The order still matters: after restoring a database copy that is older than the object store, recording reconciliation deletes the recordings it no longer finds referenced once its grace period expires. For a store it did not restore, the restore script can only stop those deletions, by setting `orphanRecordingGraceDays` to 0 so that the sweep lists orphans without deleting them; it cannot reconcile the two. |
| **Noticing when something breaks** | `scripts/verify-install.sh --quiet`, run from cron, reports scheduled jobs that stopped succeeding, the email outbox, the database disk and certificates close to expiry, and prints nothing while all is well. The Prometheus alert rules still cover only the application, the database, the bridges and TURN, so an installation that relies on them does not see the scheduled jobs, the email outbox, retention or disk space, which are the things that break silently. The GDPR cleanup fails its job when any part fails (it answers `500` with the list of failed parts), except the deletion of files from the object store, which is best effort; the other scheduled routes still report success when individual items fail. What is needed: alerts on that perimeter, and the other routes failing their job when an item fails. See [Monitoring and health](operations/monitoring.md) and [Scheduled and background jobs](architecture/background-jobs.md). |
| **Being able to go back** | After an installation or an upgrade, `scripts/verify-install.sh --call` checks that two participants can join a room and hear and see each other, but nothing runs it automatically, in CI or on a schedule, against a real installation. [Upgrades and rollback](operations/upgrades.md) describes rollback, which cannot be complete yet. Migrations are additive by policy, so a rollback leaves the newer schema in place under the older release; the way back to the older schema is the backup taken before the upgrade. The auxiliary images (recorder, recorder controller, post-production workers, captions) follow the release tag, so a rollback moves them too, unless an installation pins them to `:dev` or to a tag of its own. The patched Jitsi web image is versioned separately, with a tag of its own for each patch revision, so a release rollback does not move it. |

## Next

| Item | Where things stand |
|---|---|
| **Participant tracks without the post-production pipeline**<br/>*open since July 2026* | The raw per-participant audio is deleted once the multitrack transcription has completed. An installation that records but does not run AI post-production never reaches that step. There, tracks that are never transcribed are deleted when the event's retention expires (`multitrack-purge`, which the chart schedules when the recorder or AI post-production is on, and which the `cron` service of Docker Compose also runs), and their rows (`RecordingTrack`) go with the next GDPR cleanup. Until then, recording reconciliation recognizes the track objects and their manifest; a track still present after the event's and the recording's retention counts as an orphan, and is deleted after the grace period (`orphanRecordingGraceDays`). Recording without post-production is the most likely configuration for an administration that reuses the platform. See [Recordings, voice data and AI outputs](privacy/recordings-and-ai.md). |
| **Accessibility: a measurement, not a statement**<br/>*open since July 2026* | The accessibility statement page (`/accessibility`) exists and follows the required model, but it defers the actual conformance status to an evaluation that has not been carried out. The browser tests run an automated check (axe-core, WCAG 2.1 levels A and AA) on the public pages, the waiting room, the administration area and the live room, with the Jitsi conference left out, and keyboard tests cover the skip link, the language selector, registration without a mouse and the administration menus. An automated check sees only part of the criteria. The product is subject to legal accessibility obligations (Legge Stanca, the Italian accessibility law), and for such a product a statement that it is "designed to conform", without a measurement, cannot be defended. |
| **Live captions**<br/>*open since October 2026* | Captions over the video while the event runs answer WCAG 2.1 success criterion 1.2.4 (Captions, Live, level AA), which covers live audio in synchronized media; EN 301 549, and through it the Italian accessibility rules, include that criterion. The service is in the codebase and on by default ([Live captions](architecture/live-captions.md), [ADR-018](adr/018-live-captions.md)): Jitsi's bridge streams each speaker's audio to a gateway, a streaming recognizer transcribes it on CPU inside the cluster, and the room shows the text with the speaker's name. Italian numbers are written as digits, captions start without a moderator in the room, and an event can keep a transcript built from the captions (`captionsTranscriptEnabled`, off by default), with the voices of the people who consented. What is missing before it can be called done: a sizing measured on the cluster's node types, because the figures come from a desktop CPU (`infra/captions/bench/` runs the same measurement as a Job); and an accuracy measured on real events and stated in the accessibility statement, not assumed from read speech (`infra/captions/bench/event_wer.py` measures one event against its transcript corrected by a person). |
| **Per-person consent, applied at capture**<br/>*open since July 2026* | Consent to having one's own voice recorded and transcribed is asked at registration and in the waiting room, and stored. The per-participant recorder and the transcript built from live captions keep only the voices of people who gave it: a voice the portal cannot attribute to a person who consented is not recorded. The composite recording of the room is different: it contains every voice, and the AI transcript, summary and translations made from it contain every voice too, while the consent text says that the voice of someone who declines does not enter the transcript. Consent is also still a gate checked in the browser: the server issues the conference token without it, and speakers and moderators have no consent step of their own. What is missing: a consent text that says what each kind of recording keeps; the passages of people who did not consent removed, or marked as not transcribed, in what is kept from the composite recording; a consent step for speakers and moderators; and a withdrawal that reaches tracks, transcripts and AI outputs. The `Registration` model also has three fields for consent to transcription, summary and translation (`aiConsentTranscript`, `aiConsentSummary`, `aiConsentTranslation`) that nothing writes and nothing reads. |
| **Recording state held by the server**<br/>*open since October 2026* | The REC indicator that participants see is derived in each browser from the conference's own events. The recording time shown to whoever runs the event comes from the portal, which keeps the start and stop reported by a moderator's browser in the room's timeline, so it does not restart from zero when someone re-enters. The state still comes from a browser: it has to be read from the conference server and kept by the portal, so that every participant sees the same indicator and the same elapsed time. Stopping and restarting the recording during an event also leaves the event with only the last segment as its video: the segments need to be listed and joined, or chosen, in post-production. |
| **Presentation stage in the room**<br/>*open since October 2026* | A PDF presented from the event's materials occupies only part of the room's page. What is missing: a stage where the document takes the whole area and the call shrinks to a movable thumbnail of who is speaking, a full-screen mode with page controls for whoever presents, the side panel closing by itself while a presentation runs, and a view with the content only for the audience. |
| **Entering without watching the clock**<br/>*open since October 2026* | A participant who arrives early waits in the waiting room and has to watch for the start to press the join button. What is missing: entering by themselves when the event starts; an audio and video check offered as a step of its own before the event, which today is a field of the waiting-room card; and a short guide to the room for people who use it for the first time. |
| **Post-production failures that can be seen**<br/>*open since October 2026* | Speaker separation that fails, for example because the download of its model is refused, degrades silently to a single voice: the transcript has one speaker and only the worker's log says why. The models are also downloaded when the worker starts, instead of being kept inside the installation. A multitrack recording whose capture was interrupted, and that no later capture completes, gets no post-production job. A rerun always chooses the per-participant tracks when there are any, even when they are partial and the composite video would give a better transcript. Cancelling a pipeline does not stop a worker that is already running it. Each of these needs to be visible in the administration area, or not to happen. |
| **Playwright E2E suite**<br/>*open since March 2026* | The browser tests cover the way into the waiting room up to the join button: after registration, with a personal or moderator link, on re-entry through the event cookie, and through the guest name form on a `LIVE` event. They also guard the color of the institutional top band, run Q&A, polls and the `.ics` download through the routes the room uses, switch the event page from Italian to English, and follow an erasure request from the email to the confirmation. In the administration area, the menu of the event cards and the tabs of the event page are driven in a browser, and accessibility and keyboard checks run on public, waiting-room, administration and live-room pages. None of the tests enters the conference, and chat across several replicas is not covered. The E2E job is non-blocking, like CodeQL static analysis and Scorecard, so today none of the three protects against a regression. See [Testing](development/testing.md). |

## Later

| Item | Where things stand |
|---|---|
| **Access control on chat attachments**<br/>*open since July 2026* | Today an attachment is protected by an address that cannot be guessed (see [known limitations](#known-limitations-of-shipped-features)). The route that serves it evaluates no authorization. Real access control needs a cookie scoped to that route and re-read on every request, so that an added password or a closed event takes effect at once. A token in the URL is not enough. It would be either the reader's durable credential, which leaks during screen sharing, or a self-contained capability that ignores the event's live state. See [Security architecture](architecture/security.md). |
| **Jitsi containers hardened like the portal**<br/>*open since October 2026* | The portal, its scheduled jobs and the AI worker run without root, with a read-only root filesystem, no Linux capabilities and the default seccomp profile. The Jitsi pods (web, Prosody, Jicofo, the bridge, Jibri) keep the defaults of the upstream images: the image's user, a writable filesystem and the default capabilities, and Jibri adds `SYS_ADMIN` for its browser. The work is a security context for each Jitsi component, as far as each image allows, starting from those that need no privilege, and a written account of what Jibri cannot drop. See [Runtime hardening](architecture/security.md#runtime-hardening). |
| **Network policies on by default, for every pod**<br/>*open since October 2026* | `networkPolicy.enabled` is off by default. When it is on, it covers the portal pods and, when they are enabled, the database backup job, the Jibri pods (incoming traffic only), the live-captions pods and the CPU translation engine. The work: run it on a reference installation, turn it on by default where the cluster's network plugin enforces policies, and extend it to the other scheduled jobs, the bridge scaler, the recorder controller and bots, the post-production orchestrator and workers, and the other Jitsi pods, whose traffic it does not describe today. See [NetworkPolicy](architecture/security.md#networkpolicy). |
| **Encrypted traffic inside the cluster**<br/>*open since October 2026* | Inside the cluster, the ingress, the jobs and the portal talk plain HTTP, and the chart's Redis URL uses no TLS. The work: TLS towards Redis, which both the in-cluster subchart and managed services support, and an option for encrypted traffic between the ingress and the portal for installations whose policy asks for it. See [Trust boundaries and surfaces](architecture/security.md#trust-boundaries-and-surfaces). |
| **Instance configuration that can be exported**<br/>*open since October 2026* | The installation's settings, templates and texts are changed from the administration area, one installation at a time, and cannot be exported. Exporting, importing and versioning them would let an administration carry a configuration from a test installation to production, keep its history, and share it with another body. |
| **Distributed rate limiting**<br/>*open since July 2026* | The rate-limit counter lives in the memory of a single process, while the chart runs more than one application replica by default. Every limit is effectively multiplied by the number of replicas. The fix is a shared counter on Redis, plus a decision on what to do when Redis does not answer. Redis is already on the realtime path, so this choice brings in the high-availability item under [Conditional](#conditional). |
| **Client addresses behind proxies and over IPv6**<br/>*open since September 2026* | Per-IP limits key on one `X-Forwarded-For` entry chosen by counting hops (`TRUSTED_PROXY_HOPS`), not by matching a list of trusted proxy addresses. A request that skips the front proxy and reaches an ingress that appends to the header can therefore choose its own entry, so the chain must not be skippable ([Configuration reference](CONFIGURATION.md#client-address-and-rate-limits)). Keys are also whole addresses: a client that controls an IPv6 `/64` can rotate through it and escape every per-IP limit. Grouping IPv6 keys by prefix changes the audit log and the guest chat identifiers too, so it needs a key function of its own. |
| **Machine text and revised text, distinguished everywhere**<br/>*open since July 2026* | For transcripts, the machine version is kept and the editor shows the two side by side. For summaries and translations the machine version is kept at the first correction, but the editor does not show it. The public site and the downloads say that a person revised a text, but not which lines, and readers cannot see the machine version. |
| **Post-event report on request**<br/>*open since October 2026* | The AI summary of a recording sees the transcript, the agenda and a timeline of the room (questions, polls, counts of chat activity), and it starts by itself when a recording is ready, before any feedback has been collected. A separate event report is requested by staff after the event: it also reads the post-event feedback, the agreement and disagreement expressed on the agenda and the chat without names, it works for an event without a recording, and once staff publish it the event page shows it with the platform's figures, charts and a concept map. |
| **Event report export**<br/>*open since March 2026* | This would put statistics, Q&A, polls and participants in a single downloadable document. The data is already aggregated on the server, where it feeds the public post-event page and the recap email, but it never ends up in a file. There are several partial exports in CSV, text and subtitle formats, and none of them is the report. The project has no library that generates PDFs yet. |
| **Full-text search in transcripts**<br/>*open since April 2026* | Today the video library searches only titles and descriptions, and search inside a transcript runs in the browser over what has already been downloaded. Adding an index is not enough. The text lives in the object store, and the copy in the database is encrypted, so a plaintext index would be a new surface of personal data. A design decision has to come first. |
| **Moderator markers and chapters**<br/>*open since April 2026* | Automatically generated chapters exist, and when the event uses the agenda they follow its topics as the host starts them. What is missing are markers that whoever runs the event can set at any moment, outside the agenda. Personal bookmarks exist, but they live in the browser of the person who sets them, while moderator markers would be shared and stored on the server. |
| **Documented public API**<br/>*open since March 2026* | The OpenAPI document is served publicly at `/api/openapi.json`, readable cross-origin, and the operations it declares are accurate. But it covers only a minority of the routes, with whole route families missing, and its version is the application's version. A documentation interface can be published only after better coverage and a versioning policy: an API declared public is a commitment to stability. See [API surface](architecture/api.md). |

## Recurring events and series

There are two typical cases, with different needs:

- a fixed-cadence series: a stable weekday, with the date confirmed each time;
- a moving-date series: periodic, but often rescheduled by a few days.

Today an occurrence is created by duplicating the previous one, and a recurrence rule only proposes its date (see [From creation to recap](architecture/event-journey.md#duplication-and-series)). The series does not exist as an entity: nothing owns the canonical configuration and no scheduler consumes the rule.

In the proposed design, the series owns the configuration (capture flags, retention, languages, permissions) and each occurrence inherits it, with the option to depart from it case by case, so that no flag is lost by oversight. The cadence only suggests a date: the next occurrence is created as a draft (`DRAFT`) with a proposed date, which the organizer confirms, moves or skips.

Recording and AI post-production stay per occurrence. The series adds configuration inheritance and an aggregated view, and leaves the capture model unchanged.

## Known limitations of shipped features

These features have shipped. Each has a limit worth knowing before you rely on it.

| Area | The limitation |
|---|---|
| **Chat attachments** | Protection comes from an address that cannot be guessed and from deleting the file on moderation or when retention expires. It is not access control evaluated on every request, so whoever has the link can see the attachment, even after the event has closed. |
| **Multitrack recording** | If the conference drops mid-event, capture closes with what it has collected and does not reconnect. The truncated recording is then processed like any other. The administration area shows a partial recording with no sign that it was interrupted. See [Recording](architecture/recording.md). |
| **Keeping per-participant tracks** | An event set to keep its per-participant tracks (`retainParticipantTracks`) keeps them until the recording's retention expires, and recording reconciliation recognizes the track objects and their `tracks.json` manifest until then. A track still present after that counts as an orphan, and reconciliation deletes it after its grace period unless an administrator marks it **Keep** on the **Orphans** tab. See [Recording](architecture/recording.md#known-limitations). |
| **Transcript reliability index** | It is computed from the scores produced by speech recognition, read from the current artifact. After a manual revision, those scores are still attached to a text that a person has rewritten, so the percentage no longer describes what is on screen. |
| **Idle detection** | Part of the activity signal is platform-wide: bridge statistics are not broken down by room, and a participant on any bridge counts as activity for every `LIVE` event. While one event has people in it, other live events whose rooms are empty do not reach `IDLE` and keep counting toward the desired number of bridges. See [Scaling the media plane](architecture/scaling.md#known-limitations). |
| **Interface in 24 languages** | If a translation key is missing, the text falls back to Italian, not English. See [Languages and localization](architecture/i18n.md). |
| **Waiting-room square** | Presence is rate-limited per IP address and per app pod, so in an office behind one NAT address only a few people at a time stay visible in the square. Names are shown only to people with access to the room (a moderator, speaker or registration link, or a guest while the room admits guests); whoever knows only the address sees how many people are there. While a live event admits guests, that includes anyone with the link. See [The waiting room and the square](architecture/waiting-room.md#known-limitations). |
| **Invitations** | Nothing sends invitations: no route generates the personal link or queues an invitation email. When an event is open only to invitees, by its own choice or by the site setting, the list serves as the set of addresses allowed to register, and the organizer has to tell the invitees by other means. An event that follows the site setting still admits guests while live unless guest access is also turned off. See [From creation to recap](architecture/event-journey.md#invitation-only-registration). |
| **Material visibility** | Visibility decides which lists show a material, not who can open it. An uploaded file stays downloadable from its `/api/assets/…` URL by anyone who has the URL, in every phase. In the waiting room only the notice board of the square lists materials, those visible at that moment; the classic view, the default on phones, lists none. See [From creation to recap](architecture/event-journey.md#materials-and-agenda). |
| **Organization role and type at registration** | Of the three switches, only `requireOrganization` makes its field mandatory, in the form and in the registration route. `requireOrganizationRole` and `requireOrganizationType` show the role and the type of public body in the form as plain fields, and nothing requires them: despite their names, turning them on adds a field, not a guaranteed value. |
| **Event questionnaires** | The questions step has no check before submission. A question left incomplete makes the server reject the whole questionnaire, including the question templates selected alongside it, and the failure is reported only after saving. |
| **Content always in Italian** | The default language and the active languages can be changed from the administration area. But an event's title and description, and a question's text, are accepted only if the Italian version exists. The translation tabs show only the active languages. If Italian is not among them, the tab to write it in does not appear, and the event cannot be created. |
| **Email in five languages** | The interface is in 24 languages, but emails come in Italian, English, French, German and Spanish (`EMAIL_LOCALES` in `app/src/lib/email/lingua.ts`). People who use another language receive English, with links to the page in their own language. The texts that can be customized from the administration area cover the same five languages. See [Email and calendar](architecture/email.md). |
| **Test coverage** | Coverage is concentrated on library logic. Many API routes have no tests of their own, and rendering tests cover a minority of the components. The thresholds in `app/vitest.config.ts` are a ratchet on the measured value: they stop coverage from falling, but they do not claim it is good enough. |

## Conditional

These items answer real needs but are not planned: each is large, niche, or needed only in specific cases.

- **SPID/CIE**: sign-in for participants with the Italian public digital identity systems.
- **Calendar invitations with a reply**: add-to-calendar links cover Google, Outlook and Yahoo, and the event downloads as `.ics`, but the calendar invitation attached to the confirmation and reminder emails does not ask for a reply. What is missing is a reply that becomes a registration, and synchronization with organizational calendars.
- **Breakout rooms**: Jitsi's native breakout rooms are hidden in the interface, not disabled on the server. Exposing them is a product decision rather than new development, but it has to settle what chat, Q&A and controls do when participants are in different sub-rooms. Workshops and co-design sessions are where they are asked for.
- **Blurring faces and voices** before a recording is published.
- **View-only live stream** for an unlimited audience, without loading the bridges.
- **Mobile app**: the web interface is responsive and works on a phone today. Installing it as a web app (a progressive web app) is the smaller step.
- **Multi-camera recording**: speaker and slides as separate recordings. The current multitrack recording is audio only, and exists to attribute speech.
- **Event-template catalog shared across public bodies**: event templates are internal to one installation today, and this item depends on the multi-body item above.
- **High availability for the Redis tier**: Redis is already on the realtime path (chat, live controls, bridge state). When Redis is unavailable, that path degrades without blocking mutations: a publish on a connection that is not ready gives up at once, and a wait for a response has a deadline. Some commands can still wait without limit, including the write of the bridge-state snapshot. High availability becomes a requirement once distributed rate limiting also relies on Redis.
