─── Copia del database ───────────────────────────────────────
  CronJob {{ $fn }}-backup ({{ dig "schedule" "" $b }}, UTC): pg_dump nel volume
  {{ $claim }}, ultime {{ dig "retention" 7 $b }} copie in /backup/pa-webinar-<data>.dump.
  Contengono dati personali. Sullo stesso disco del database non
  proteggono dalla perdita del nodo: copiale anche altrove.
{{- if $inAttesa }}
  Il volume {{ $claim }} non è ancora legato. Se la sua classe lo lega
  al primo pod che lo usa (WaitForFirstConsumer, come local-path su k3s),
  resta Pending fino alla prima copia, e `helm upgrade --wait` lo aspetta
  fino alla scadenza. La copia qui sotto lo lega subito, e prova che le
  copie funzionano.
{{- end }}
  Una copia subito:
    kubectl -n {{ $ns }} create job {{ $fn }}-backup-$(date +%s) --from=cronjob/{{ $fn }}-backup
  Un pod con il volume, per elencare le copie e portarle fuori dal nodo,
  che si chiude da solo dopo {{ div (int (dig "activeDeadlineSeconds" 3600 $b | default 3600)) 60 }} minuti:
    J={{ $fn }}-tools-$(date +%s)
    kubectl -n {{ $ns }} create job $J --from=cronjob/{{ $fn }}-backup-tools
    kubectl -n {{ $ns }} wait job/$J --for=jsonpath='{.status.ready}'=1
    kubectl -n {{ $ns }} exec job/$J -- ls -l /backup
    (umask 077; kubectl -n {{ $ns }} exec job/$J -- cat /backup/<file> > <file>)
    kubectl -n {{ $ns }} delete job $J
  Ripristino di una copia: scripts/restore.sh del repository, non un
  pg_restore a mano. Ferma portale e lavori pianificati, ripristina in
  una sola transazione e riaccende tutto nell'ordine giusto:
    scripts/restore.sh --context <contesto> --namespace {{ $ns }} --release {{ .Release.Name }} \
      --from-dump <file> --dry-run
  e, se il piano va bene, lo stesso comando con --yes al posto di
  --dry-run (--kubeconfig <file> al posto di --context, se serve).
{{- end }}
